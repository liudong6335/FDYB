## 一、定位与目标

### 1.1 本阶段的边界（极其重要）

本文档只服务于**原型阶段（Prototype）**，其唯一目的是：

> **用两个"够用"的 AI 互相打，跑通全部核心机制，验证"囚徒困境收益结构"在特定参数下成立，并调出一组能让机制成立的初始数值。**

本阶段**不做**以下事情（这些属于项目中后期）：

- ❌ 多人格 / 多角色卡（Guardian、Hunter、Scholar……）
- ❌ 行为树 / 机器学习 / 复杂战术
- ❌ 真人手感调优、电竞平衡
- ❌ 网络同步、防作弊、断线重连

本阶段**只做**一件事：

> ✅ **证明这套机制的收益结构"活着"——在给定参数下，四种基本策略（双停 / 双杀 / 单方杀 / 响应式）的期望收益满足囚徒困境的偏序关系，且全部核心行为可被稳定触发。**

### 1.2 为什么用同质化 AI（两个完全相同的 AI）

1. **隔离变量**：AI 越复杂，行为越不可控，你就越难判断"机制没跑出来"到底是**数值问题**还是**AI 太蠢**。原型阶段要让 AI 逻辑尽量薄、尽量透明。
2. **公平性即对照性**：两个相同 AI 对打，对称性天然趋向 50/50。**但这一点本身不能当作平衡性证据**（详见第十节 P1），只能用于暴露出生点/标签不对称等结构性 bug。
3. **快速迭代**：不需要设计人格差异，先把"机制有效性清单"跑通，再谈多样性。

> ⚠️ **重要澄清（回应评审 P0-2）**：同质 AI + 对称出生点 + 对称资源的**默认状态**，行为会高度同步（要么一起杀、要么一起停），**很难自然涌现** M2/M3/M4/M7 所需的"一方强一方弱、一方杀一方停、一方囤塔一方放塔"等非对称局面。即便随机掉落偶尔打破对称，那也只是随机噪声，20-30 局里 M3/M5/M7 很可能一次都不出现；为了把它们"调出来"而调参，反而会污染结论。
>
> **因此本阶段保留"同质 AI"，但明确区分两种运行模式**：
> - **对称自对弈（默认）**：只用于 A 层烟测的 M1/M8 + B 层收益矩阵的基准行（双停/双杀）。**不作为 M3-M7 的触发来源。**
> - **受控场景注入（新增，第六节）**：通过预置血量差、战力差、圣物持有、囤塔数量差异，专门驱动 M3-M7 的非对称行为。这**不破坏 AI 的同质性**——AI 的决策逻辑完全相同，只是初始状态被人为偏移。

### 1.3 核心成功判据（原型阶段的"够用"标准）

不需要"最优数值"，只需要证明：**囚徒困境的收益结构能涌现，且满足 T > R > P > S。** 具体要求见第六节（A / B / C / D 四层，其中 B 层为严格的 T > R > P > S 成立性证明）。

## 二、设计哲学：AI 不是"对手"，而是"机制探测器"

### 2.1 核心认知

原型阶段的 AI **不需要聪明，只需要"有感知、有记忆、有基本前瞻"**。它的角色是：

> **一个能对游戏状态变化做出可预期反应的"探测器"，用来探测这套机制在特定参数下会不会演出设计者想要的行为与收益结构。**

举例：
- 如果**杀怪权重**从 3 调到 10，AI 的杀怪频率应当**下降**（因为它能感知进度增速）；
- 如果**结盟时长**从 30 秒调到 15 秒，AI 的结盟意愿应当**下降**；
- 如果**圣物减伤**从 50% 调到 80%，持有圣物的 AI 应当**更倾向于 solo**。

**只要 AI 能对参数变化做出符合设计预期的行为改变，机制测试即为有效。** AI 不需要多聪明，只需要"够用"。

### 2.2 if/else 不是问题，"短视的 if/else"才是

纯贪婪、无记忆、无前瞻的 if/else 会让机制跑不出来：AI 永远无脑杀怪（因为即时战力收益 > 延迟 Boss 代价），导致数据被污染，让你误判为"数值有问题"。

解决办法不是升级到行为树，而是在 if/else 中补入**三项能力**（详见第五节）：

1. **趋势感知**（看到延迟代价）
2. **状态记忆**（记得最近发生了什么，**包括囤塔与圣物状态**）
3. **终局触发**（时间压力下的战略优先级切换，**包括对 Boss 结盟的应对**）

## 三、AI 决策架构（极简三层）

```
┌──────────────────────────────────────────────┐
│  Layer 3 · 终局战略层（Game-End Strategy）    │
│  · 进入最后 N 分钟 / 峰顶决战圈时的全局优先级 │
│  · 含：心争夺 / solo 或结盟抉择 / Boss 结盟应对│
├──────────────────────────────────────────────┤
│  Layer 2 · 状态记忆层（State Memory）         │
│  · 短期标记、计时器、趋势采样                 │
│  · 含：圣物持有 / 背包囤塔 vs 已放塔 / 结盟状态│
├──────────────────────────────────────────────┤
│  Layer 1 · 趋势感知层（Trend Awareness）      │
│  · 对延迟代价、共享进度的粗略感知             │
└──────────────────────────────────────────────┘
                ↓ 输出"情境变量"
         ┌──────────────┐
         │  行为选择器   │  ← 本质就是一组带优先级的 if/else
         └──────────────┘
```

### 3.1 关键设计：行为优先级（固定，不学习）

AI 不做"收益最大化计算"，而是按**固定优先级**选择当前行为。这正是"够用"的关键——逻辑透明、可预测、易调试。

```
优先级（从高到低）：
1. 生存（血量极低 → 逃跑 / 治疗 / 申请结盟 / 应对 Boss 结盟）
2. 响应事件（心出现 / 结盟申请 / 被攻击 / Boss 结盟发起 → 立即反应）
3. 终局行为（最后阶段 → 直奔 Boss / 争夺心 / 决策 solo 或结盟）
4. 资源管理（趋势感知 → 杀怪 or 停手 / 开箱 or 狩猎 / 囤塔 or 放塔）
5. 默认（移动、巡逻、补刀）
```

当高层行为不满足触发条件时，自动 fallthrough 到低层。**这避免了"AI 永远无脑杀怪"**——因为"生存"和"终局"优先级更高，会在关键时刻覆盖"杀怪"。

## 四、核心感知：让 AI 看见"延迟代价"（防蠢的关键）

### 4.1 趋势感知：不再只看"当前值"，而是看"增速"

AI 每 `T_sample` 秒记录一次共享 Boss 进度，计算最近窗口内的**平均增速**：

```
progressRate = (currentProgress - progressPrev) / T_sample
```

据此进入三种"态势"：

| 态势 | 判定 | AI 行为倾向 |
|------|------|------------|
| `SAFE` | 增速 < 阈值低 | 可正常发育（杀怪 / 开箱） |
| `WATCH` | 阈值低 ≤ 增速 ≤ 阈值高 | 收缩风险：优先杀高价值怪、少杀自然怪 |
| `URGENT` | 增速 > 阈值高 | 抑制杀怪：只杀"战力瓶颈"必需怪，其余停手 |

> **这正是防止"永远该杀"的核心**——当进度涨太快，AI 会主动停手，因为"趋势感知"让它看到了 20 秒后的代价。

### 4.2 共享进度的"信息延迟"模拟

为贴近真实机制（进度条每 20-40 秒刷新），AI 感知到的进度值也做**离散刷新 + 小幅误差**，而非每帧精确。这样：
- 保留"背叛窗口"：AI 在某个刷新周期内看不到对方偷偷杀怪；
- 避免 AI 变成"全知全能的数值计算器"，行为更贴近真人。

> 注意：原型阶段此项为**可选开关**，默认关闭（让 AI 用精确值，便于先跑通机制）；机制跑通后再开启，检验"信息延迟"是否破坏囚徒困境。

## 五、状态记忆与终局触发（防蠢的另外两块）

### 5.1 短期记忆（几秒到几分钟的标记 / 计时器）

| 标记 | 含义 | 对行为的影响 |
|------|------|------------|
| `recentlyBetrayed` | 结盟结束后 N 秒内 | 优先攻击前盟友 |
| `recentlyHitByBoss` | 最近被 Boss 打过 | 更倾向于结盟 / 逃跑 |
| `killStreak` | 连续杀怪计数 | 过高时主动停手一段时间（自我抑制） |
| `lastAllyTime` | 上次结盟距今 | 控制结盟冷却节奏 |
| `hasRelic` | 是否持有圣物 | 终局 solo / 结盟选择（详见 5.3） |
| `towerStock` | 背包中未放置的塔材料/塔数量 | 终局放塔决策（详见 5.3） |
| `towerPlaced` | 已放置的塔数量 | 战力实时计入，结盟期间锁定 |
| `currentAlly` | 当前结盟对象（Player / Boss / None） | 区分"玩家间结盟"与"弱者与 Boss 结盟"（详见 5.4） |

这些不是复杂逻辑，只是**让当前决策能参考近期历史与资源状态**，避免"逐帧失忆"。其中 `hasRelic`、`towerStock`、`currentAlly` 是 v0.3 新增，用于补齐囤塔/圣物/Boss 结盟的行为缺口。

### 5.2 终局触发（时间压力下的战略切换）

当满足以下任一条件时，AI 切换为"终局模式"：
- 游戏时间进入最后 N 分钟；
- 海平面收缩至峰顶决战圈；
- Boss 已进入可挑战状态。

终局模式的行为覆盖：
- 不再开箱、不再杀无关小怪，直奔 Boss 区域；
- 结盟冷却好了且自身血量 < 阈值 → **主动申请结盟**；
- 持有圣物且 Boss 血量 < 阈值 → **尝试 solo，不再结盟**；
- 心出现 → **立即争夺**。

> 这保证了"Boss 战 / 心争夺 / 结盟"等终局机制**具备被触发的条件**。（但注意：仅有条件还不够，M3-M7 的非对称前提需靠第六节"受控场景注入"提供，见评审 P0-2/P0-3。）

### 5.3 终局战略的两类关键决策（v0.3 新增）

**A. 圣物获取与保护（回应评审 P0-3，驱动 M5）**

AI 必须显式维护 `hasRelic` 状态，并在终局使用该状态：
- **持有圣物时**：若 Boss 血量 < 阈值，优先选择 solo（不再结盟），因为圣物提供对 Boss 的减伤；若自身残血，仍优先保命（生存优先级最高）。
- **未持有圣物时**：优先选择结盟，或尝试击杀圣物持有者以抢夺。
- **保护与抢夺**：持有圣物时避免无意义交战（防止掉落），无圣物时主动压制持有者。

> 这样 M5"有圣物者 solo 成功 / 无圣物者 solo 失败"才能**自然发生**，而不是靠人工造局。

**B. 囤塔 vs 放塔（回应评审 P0-3，驱动 M7）**

AI 必须区分 `towerStock`（背包囤塔，结盟期间锁定、不计入战力）与 `towerPlaced`（已放塔，实时计入战力）：
- **发育期**：优先将塔材料留在背包（`towerStock`），作为终局的"战略储备"——这天然形成"囤塔不计战力、放塔后实时计入"的战力构成。
- **结盟锁定**：结盟期间 `towerStock` 不可放置（锁定），结盟结束解锁。
- **终局 / 结盟后**：将 `towerStock` 一次性放置，形成"放塔风筝"，为弱者提供翻盘路径。

> 这样 M7"囤塔者结盟后放塔翻盘"才能自然发生。若 AI 逻辑里根本没有囤塔决策，M7 永远不会触发。

### 5.4 Boss 作为第三方：边界必须写清（v0.3 新增，回应评审 P0-3）

原型阶段必须明确回答：**Boss 是"可决策的第三方"还是"纯环境木桩"？** 这块边界不写清，M3/M4 的事件口径会模糊。本阶段采用以下定义：

> **Boss 是"带独立决策的第三方"**——AI 不需要复刻 Boss 内部的 10 秒局势快照；Boss 按《Boss功能开发清单》运行，AI 只消费公开的 `BossState`、状态变化和事件。AI 接入至少需要处理：
> 1. **Boss 可被结盟对象**：区分"玩家 + Boss"与"玩家 + 玩家"结盟路径（`currentAlly` 标记）。
> 2. **Boss 结盟事件**：处理申请、接受、拒绝、开始、结束和翻脸事件，并以公开状态更新自身决策。
> 3. **Boss 战斗状态**：读取 Boss 血量、强度状态、强化层、当前目标和公开仇恨/交战信息；不读取 Boss 内部快照对象。

**AI 对 Boss 结盟的应对行为**（必须实现，否则 M3/M4 无事件源）：
- 当对手与 Boss 结盟时，AI 应识别"我成了被追杀方"，行为切换为**风筝 / 拖延 / 抢先削弱 Boss**。
- 当自身为弱者时，AI 主动发起"弱者 + Boss"结盟申请。

> 明确这一点后，M3/M4 的结盟/翻脸事件才有统一口径，不会与"玩家间结盟"混淆。

### 5.5 AI 决策伪逻辑（参考实现，便于对齐）

```
每帧 / 每决策周期：

  // Layer 3 · 终局战略
  IF 进入终局模式:
       IF 心已出现:                          → 行为 = 争夺心
       IF 有圣物(且未被追杀) AND Boss血量<阈值: → 行为 = solo Boss（不结盟）
       ELSE IF 结盟可用 AND 血量 < 阈值:
            IF 自身为弱者 AND Boss未结盟:   → 行为 = 申请"弱者+Boss"结盟
            ELSE:                            → 行为 = 申请"玩家间"结盟
       ELSE IF towerStock > 0 AND 结盟已结束: → 行为 = 放置囤塔（风筝/翻盘）
       ELSE:                                 → 行为 = 逼近 Boss

  // Layer 2 · 事件响应（含 Boss 结盟发起）
  ELSE IF 被攻击 / 结盟申请到来 / Boss结盟发起: → 行为 = 立即响应

  // Layer 1 · 趋势感知下的资源管理
  ELSE IF 态势 == URGENT:                     → 行为 = 抑制杀怪（只补必需怪 / 开箱回血）
  ELSE IF 态势 == WATCH:                      → 行为 = 选择性杀高价值怪
  ELSE:                                      → 行为 = 正常发育（杀怪 / 开箱 / 适度囤塔）

  // 生存始终最高优先级（贯穿）
  IF 血量 < 生存阈值:
       行为 = 逃跑 / 治疗 / 申请结盟（覆盖以上）
```

> 说明：这是**逻辑描述，非代码要求**。重点是**保留三层结构与固定优先级**，并显式包含 5.3、5.4 的两类新决策。

### 5.6 决策分化层：局势快照、对手快照与路线分支（v0.5 新增）

本节解决"同质 AI 默认同步，M2/M3/M7 所需非对称局面难以自然涌现"的运行层问题。原则：**AI 仍是同一个决策逻辑，不使用人格差异；非对称来自感知相位、可见信息与成长随机性造成的输入不同，而不是行动随机。**

#### 5.6.1 局势快照：同周期、固定相位差

- 每个 AI 按**同一周期**（如 10s）采样局势，但相位固定错开。例如 A 在 `gameTime % 10 == 4` 时采样，B 在 `gameTime % 10 == 9` 时采样。
- 相位永远错开且**不会周期性对齐**；每个 AI 在两次采样之间沿用最近一次快照。
- 实现为可开关参数 `snapshotPhaseOffset`，**默认关闭**（两 AI 同相位，先跑基线）；机制跑通后开启做分化测试。
- 使用**游戏累计时间取模**，不用真实秒表 / 墙上时间，保证暂停与 `8x` 加速下仍一致。
- 当阈值事件发生在两个采样点之间时，后采样的 AI 会先看到新状态并先决策，另一方仍按旧状态行动。领先 / 落后的信息时效**轮流切换**，不固定偏向某一侧。
- 该延迟只作用于局势 / 共享进度 / 对手参数快照；**被攻击、结盟申请、心出现等事件仍然立即响应**。
- 玩家永久淘汰或 Boss 死亡时，所有存活 AI 立即强制刷新活动快照，不等待各自的下一个采样点；死亡结算、结盟解除和 allianceVersion 递增必须发生在刷新之前。
- 结盟开始、结束和翻脸时立即更新 `allianceState / allianceTargetId` 并递增 `allianceVersion`；AI 的目标过滤读取实时版本，其他战略快照字段不重掷。
- 正常到期按 `AllianceEndedEvent` 处理：T0 刷新目标/求生/结盟/AI 视角，T+3 惩罚仇恨生效时刷新目标仇恨排序并递增 `revengeHateVersion`。

#### 5.6.2 对手快照评估（PlayerView）

- AI 的对手信息只能来自一份与玩家 UI 对齐的 `PlayerView`，**不读取对手内部路线、意图、背包明细或内部 trust**。
- 可见字段至少包括：双方血量 / 战力差、共享 Boss 进度（按 20-40s 刷新）、对手击杀增量（从刷新后的进度推断）、塔状态与预留塔数、圣物持有、结盟状态、心 / 海平面 / 时间等公开信息。
- `PlayerView` 的刷新节奏与 UI 刷新规则一致；AI 决策代码只能消费 `PlayerView`，并用测试断言保证其字段集合与 UI 一致。
- 对手快照只输出**粗粒度推断**：`克制 / 激进 / 压制 / 合作信号 / 未知`，并累积为每个 AI 自己维护的 `trustScore`（不共享、不实时精确）。

#### 5.6.3 路线分支：不是人格，是共同决策函数

- 所有 AI 共享同一个"局势 + 对手评估 → 路线"映射；路线不是人格或角色卡。
- 接近 / 均势时路线可分支为 `克制` 或 `激进`。**双方数值接近且输入一致时选择相同路线是允许的**（同为 CC 或 DD），不要求强制"一克制一激进"。
- 路线选择使用评分而非固定概率：

```
aggressionScore = 基准风险
    + 对手近期偷杀 / 压制证据
    + 刷新窗口剩余时间（偷杀可隐藏的诱惑）
    + 对手 trustScore 扣分
    - Boss 进度增速风险
    - 自保 / 结盟需求

if aggressionScore > 激进阈值 → 激进路线
else                           → 克制路线
```

- 阈值附近使用滞回，路线切换至少保持一个快照周期，避免震荡；必须打平时使用固定种子派生的相位 / 微小扰动。
- 数值拉开时路线自然分化：领先方走压制 / 继续发育，落后方走追赶 / 囤塔 / 结盟准备。
- **不把"随机决策概率"作为分化来源**：随机只允许出现在环境机会、掉落、感知误差、快照相位等输入层，且全部可复现。

#### 5.6.4 与 Boss 快照机制的复用边界

- 可复用：周期快照容器、版本号 / 采样时间、相位偏移、事件强制刷新、死亡刷新和快照日志。
- 可复用：高频决策消费低频快照、事件通道独立立即响应的结构。
- 不可复用：Boss 的求生阈值、结盟总门禁、战力压制、仇恨公式和 Boss 专属 `slotId` 映射。
- AI 玩家必须使用自己的 `snapshotProfile`、刷新周期和输入集合；Boss 快照规则作为架构参考，不作为 AI 数值配置的默认值。
- 玩家死亡和 Boss 死亡的强制刷新属于通用事件规则，AI 玩家与 Boss 必须使用同一触发语义。
- 结盟状态的实时版本覆盖属于通用关系规则；AI 使用同一个 `allianceVersion` 语义，但结盟业务阈值仍由各自系统提供。
- 强制刷新必须递增快照版本并记录刷新原因与死亡实体 ID，保证回放可复现。
- 关键生命阈值向下跨越时立即刷新低频快照的规则可由 AI 复用，但具体阈值由 AI 自己的生存配置决定。

## 六、机制有效性清单与验收（v0.4：A/B/C/D 四层）

> ⚠️ **本节是 v0.3 最重要的修订（回应评审 P0-0）。**

### 6.0 修订动机：为什么"M1-M8 全部触发"不等于"囚徒困境成立"

v0.1/v0.2 的验收标准是"M1-M8 各至少出现一次"。但这一标准存在致命漏洞：

**第五节、第八节的 if/else 本身就预写了"血低就申请结盟、心出现就争夺、终局就直奔 Boss"。** 也就是说，即使规则层面"永远该杀"或"永远不该杀"**占优**（收益结构已经崩塌），只要参数调得巧，M1-M8 一样能**全部触发**——然后被**误判为机制成立**。

原因在于：M1-M8 是**"行为有没有发生"的触发式检查（可达性）**，而**不是"收益结构对不对"的偏序检查**。前者可由脚本硬编码触发，后者才真正定义囚徒困境。

**因此，v0.3 将验收拆分为 A、B 两层。两层都通过，才可判定机制成立。**

### 6.1 A 层：系统可达性烟测（Mechanism Smoke Test）

A 层的职责是**廉价地确认"所有系统都能跑通、无卡死、无事件缺失"**。它沿用 M1-M8 的触发式检查，但**降级为"烟测"，不再单独作为成立依据**。

| 编号 | 预期行为 | 观测方式 | 未出现时的怀疑方向 |
|------|---------|---------|------------------|
| M1 | 双方都杀怪 → Boss 提前苏醒 → 双输 | 日志：杀怪数↑、苏醒时刻↓、双输局 | 杀怪权重太低 / Boss 太弱 |
| M2 | 一方停手、一方杀怪 → 双方结局均可出现（见 6.2 B 层收益关系） | 胜负与杀怪数的相关性 | 战力成长曲线太平 / 太陡 |
| M3 | 弱者申请结盟 → 结盟成立 → 翻脸后一方获胜 | 结盟成功率、翻脸胜率 | 结盟收益太低 / 时长不合理 |
| M4 | 强者翻脸 → 弱者反杀或双输 | 翻脸事件 + 后续胜负 | 翻脸惩罚太弱 / 太强 |
| M5 | 圣物持有者 solo 成功；无圣物者 solo 失败 | 圣物持有 × 胜负 交叉表 | 圣物减伤偏离合理区间 |
| M6 | 心争夺发生，且存在易手/打断，最后一击者**不**永远获胜 | 易手次数、击杀者交付率 | 读条过短 / 尾刀收益过高 |
| M7 | 囤塔者结盟后放塔 → 出现翻盘局 | 囤塔使用率、翻盘率 | 配额/战力构成/Boss 转向 |
| M8 | 存在"双方都不杀怪"的局 → 因 Boss 强化/时间压力被迫收束，非僵局死锁 | 极端合作局的收束情况 | Boss 随时间强化机制 |

> **A 层通过标准**：M1-M8 全部至少触发过一次，**且**事件断言（6.4）全部可判定。A 层通过**只说明"系统跑得起来"**，不说明囚徒困境成立。

### 6.2 B 层：囚徒困境成立性证明（核心判据，T > R > P > S）

> ⚠️ **本节是 v0.4 的核心升级（回应"囚徒困境成立必须有可计算条件"）。**
> v0.3 的 B 层使用"策略探针 + 三条偏序关系"，但仍未把"囚徒困境成立"钉死为一个**可计算的数学条件**。本节将其升级为严格的 **T > R > P > S 排序检验**——这是"机制能跑通"与"机制成立且有效"之间的分水岭。

#### 6.2.0 核心认知："能跑通"≠"囚徒困境成立"

举一个极端反例说明为何必须单独验证成立性：

- 若**杀怪推 Boss 权重 = 0**（杀怪零代价）、**结盟时长 = 999s**（无限结盟）：跑 AI vs AI，机制能跑通（杀怪、结盟、打 Boss、抢心全部触发，日志干净、无卡死），但囚徒困境**完全不成立**——AI 无脑杀怪后永远结盟，没有任何"被迫合作→必然对立"的张力。
- 反之若**杀怪权重 = 100**，Boss 第一分钟苏醒，双方永远双输：机制照样跑通，囚徒困境同样不成立（"永远不该杀"也是无脑最优解）。

**因此：A 层只证明程序正确性；B 层必须独立证明规则层面的博弈结构。两者缺一不可。**

#### 6.2.1 动作定义（把抽象动作钉死）

先把两个**基本动作**严格定义（全文档统一口径，事件日志据此打标）：

| 动作 | 记号 | 定义 |
|------|------|------|
| **克制 / Cooperate** | **C** | 在该进度窗口内**基本停手**，只做**不推进 Boss 苏醒进度**的发育（如开箱、适度回血），**不偷杀** |
| **偷杀 / Defect** | **D** | 为了**个人战力继续杀怪**，**主动推进 Boss 苏醒进度** |

> 说明：C/D 是**进度窗口内的行为策略**，不是"永远不杀/永远杀"。一个对局可由多个窗口组成，但 B 层检验使用**整局锁定**的纯策略（见 6.2.3）。

#### 6.2.2 收益矩阵与 T > R > P > S

按"**你**的收益"构造 2×2 收益矩阵：

|  | 对手克制 **C** | 对手偷杀 **D** |
|--|:--:|:--:|
| **你克制 C** | **R**（都克制：Boss 正常苏醒，双方公平局） | **S**（你克制、他偷杀：你战力吃亏） |
| **你偷杀 D** | **T**（他停你杀：你战力占优，最爽） | **P**（都偷杀：双方战力都高，但 Boss 最早醒、最强） |

**囚徒困境成立的必要条件（必须全部满足）：**

```
T > R > P > S
```

逐项文字含义：

1. **T > R**：对方克制时，你偷杀比跟着克制更赚 → **"背叛诱惑"的来源**。若克制反而更赚，无人会背叛。
2. **R > P**：双方都克制，比双方都偷杀更容易赢 → 若都偷杀更赚，则"永远该杀"，不构成困境。
3. **P > S**：对方已偷杀时，你跟着偷杀比单方面克制好 → 否则对方背叛时你克制也不吃亏，困境同样不成立。

> **反过来：只要上述四条中的任意一条反了，机制就不再是囚徒困境，而是"永远该杀 / 永远该停 / 克制是纯送"等结构性问题。** 这是判定"机制成立"的硬门槛，不达标不得冻结数值。

#### 6.2.3 策略探针：锁定策略而非自由决策（对称自对弈）

为**隔离 AI 自主性带来的噪声**，B 层把 AI 动作从"自由决策"改为**整局锁定策略**。由外部探针（非 AI 人格）强制两个 AI 分别采用四种纯策略组合，**地图/出生点/掉落严格对称**：

| 策略组合 | A 的动作 | B 的动作 | 用途 |
|---------|---------|---------|------|
| **CC** | 克制 C | 克制 C | 基准行，应接近 50/50、双输率最低 |
| **DD** | 偷杀 D | 偷杀 D | 应双输率最高（验证 R > P） |
| **DC** | 偷杀 D | 克制 C | 偷杀方收益应最高（验证 T 最大） |
| **CD** | 克制 C | 偷杀 D | = DC 互换，**用于对称性校验** |

**对称性校验（必须执行，否则结果作废）**：

- **CD 与 DC 必须互换左右出生点各跑一组**，随后合并统计。若 `E(DC) ≠ E(CD)`（差异超出置信区间），说明地图/出生点不对称（如一侧天然靠近 Boss 刷新点），**整组结果作废重跑**。
- **CC 也应左右互换跑一组**，作为对称性基线。

每组跑 **30-50 局固定种子**，用种子组而非单局，消除随机波动。

#### 6.2.4 效用函数 U（必须显式定义，且不能让 P、S 恒为 0）

⚠️ **关键**：收益矩阵单元格填的是"你的收益"，而《分道扬镳》里"你偷杀"的后果是**双向的**——你战力占优（PvP ↑），但 Boss 更早醒更强（Boss 端 ↓）。因此 `T/R/P/S` 中的 ">" 不能是简单的"谁赢谁"，必须由**一个确定的标量效用函数 U** 统一。

**采用加权胜负效用（定义确定、全程不变、跨场景一致）**：

```
U(结局) = 1.0 × (己方最终获胜：交付恶魔之心)
        + 0.3 × (对手出局但己方未获胜，即"相对优势")
        + 0.0 × (双输 / 未分胜负)
        - 0.5 × (己方出局)
```

**每个策略组合的收益 = 该组 30-50 局的 U 均值：**

```
T = U(DC 组),  R = U(CC 组),  P = U(DD 组),  S = U(CD 组)
```

> ⚠️ **反"假通过"警告**：若 U 只算"赢=1、其余=0"，则 DD 永远双输 → P ≡ 0、S ≡ 0，排序会**机械地**变成 T > R > P = S——看起来满足 T>R>P>S，实则是效用函数过粗造成的**失真**。加入 `0.3 × 相对优势` 后，即使 DD 偶尔靠超高战力 solo 拿到部分分数，P、S 也不会恒为 0，排序才有意义。**该权重（1.0 / 0.3 / -0.5）为原型阶段起始猜测，校准理由须记入修改审计，不得中途暗改。**

#### 6.2.5 统计判据：不只是"排序对"，还要"差异显著"

**主判据（必须同时满足，第十节门禁）：**

```
(1) T_mean > R_mean > P_mean > S_mean       （严格递减）
(2) 相邻两两差异的 95% 置信区间不重叠
```

**辅助判据（防假通过，任一不满足须排查）：**

- **对称性**：`|E(DC) − E(CD)|` 的置信区间包含 0（即 DC ≈ CD）；
- **CC 非必输**：CC 的双输率 < 10%（CC 是合作最优局，若连 CC 都常双输，说明 Boss 基础强度过高，收益结构被"必输"主导）；
- **DD 最坏**：DD 的双输率 **高于** CC/CD/DC 任一组（这是 P > S 的直观体现）。

> **B 层通过标准**：主判据 (1)(2) **+ 辅助判据全部成立**，且**在 holdout 种子上复现**（防止针对训练种子过拟合）。**任一不满足 → 判定囚徒困境结构失效，不得冻结数值。** 常见失效模式见 6.2.7。

#### 6.2.6 与 v0.3 "三条偏序关系"的对应关系

v0.3 的关系 ① ② ③ 在此被**严格化**为 T > R > P > S：

| v0.3 偏序关系 | v0.4 严格等价条件 |
|--------------|-----------------|
| ① 双停优于双杀 | **R > P** |
| ② 背叛有时优、有时亏 | **T > R**（诱惑存在）**且** 在特定态势下 T 优势被 Boss 代价抵消（见 6.2.7） |
| ③ 回应有额外收益 | 由 **C 层 + D 层** 承接（见 6.2.7 与 6.3） |

> v0.3 的关系 ② "有时自食其果"在锁定策略框架下体现为：**当 Boss 进度阈值/强化幅度增大时，T 相对 R 的优势缩小**。验证方式见 6.2.7 梯度测试。

#### 6.2.7 梯度测试（验证"背叛代价随进度递增"，条件完整性）

仅跑固定阈值的一组 CC/DD/DC/CD **不足以证明结构稳健**。B 层须额外做**进度敏感度梯度测试**：

- 固定 DD 策略，分别设置 Boss 进度阈值 = 60 / 80 / 100（模拟不同进度下双杀的后果），各跑一组；
- 若三组的 DD 收益 **无显著差异** → 说明背叛代价**不随进度变化** → P 恒劣、结构退化，**条件 2 不满足**。

**预期健康表现**：随阈值降低（Boss 越易被激怒），T 相对 R 的优势缩小，DD 双输率上升。这说明"偷杀"是**有风险的真实抉择**，而非无脑最优。

> 若梯度测试或主判据反复不通过，**不要反复微调数值试图蒙混**——这通常是**机制层面的死路**（如杀怪个人收益过高、提前苏醒代价过弱），须回到规则设计层面修正，调参救不了。

### 6.3 C 层（成立性）与 D 层（体验质量）的清晰分层

**B 层的 T > R > P > S 只证明"规则结构上是囚徒困境"，不代表"剧情好看 / 数值舒服"。** 为避免把"机制成立"与"机制好玩"混为一谈（两者对应不同的修复动作），将验收进一步拆为 **C 层**与 **D 层**：

| 层级 | 职责 | 不通过时的处置 |
|------|------|--------------|
| **C 层 · 囚徒困境结构成立** | T > R > P > S + 统计显著 + 对称性校验（6.2） | **改规则**（结构性死路，调参救不了） |
| **D 层 · 体验质量（附加约束）** | 保证"成立"的同时不失趣味性（见下） | **调参**（结构对、手感差） |

**D 层附加约束（不影响"是否成立"，只影响"好不好玩"）**：

- **D-1**：CC **不能永远是 50/50 的平局**——应有发育博弈空间（M8 的"被迫收束"维度）；
- **D-2**：DD **不能必双输**——给合作留一线（否则"合作"是唯一理性选择，困境张力消失）；
- **D-3**：偷杀**有风险但非 100% 得手**（T 显著但非绝对，M2a/M2b 的张弛）；
- **D-4**：心争夺存在真实易手/打断（M6，已在 6.7 强化）。

> **关键**：C 层不通过 → 机制结构性失败，**必须改规则**；D 层不通过 → 机制成立但不好玩，**调参即可**。原型阶段的目标是**先过 C 层**，D 层作为"数值舒适度"参考，允许后续迭代。

### 6.4 受控非对称场景注入（回应评审 P0-2 / P0-3）

由于对称自对弈难以自然产生 M3-M7 所需的非对称前提，B 层与 A 层的 M3-M7 观测**统一采用受控场景注入**：**保持 AI 决策逻辑同质**，但**预置初始状态差异**。每个场景用独立种子组（30-50 局）运行。

| 场景编号 | 预置差异（初始状态偏移） | 驱动的目标 |
|---------|------------------------|-----------|
| AS-1 | 一方血量 30%，另一方 100% | M3 弱者结盟、M4 强者翻脸 |
| AS-2 | 一方战力高 30%，另一方低 | M2 杀怪 vs 停手的结局差异 |
| AS-3 | 一方持有圣物，另一方无 | M5 圣物 solo / 抢夺 |
| AS-4 | 一方背包囤塔 3 座，另一方 0 座，且已结盟过 | M7 结盟后放塔翻盘 |
| AS-5 | 一方与 Boss 已结盟（模拟中途） | M3/M4 Boss 结盟路径与翻脸 |
| AS-6 | Boss 血量 30%，双方满状态 | M6 心争夺、尾刀化检测 |

> **关键**：AI 逻辑完全相同，只是**初始状态**被偏移。这既保留了"同质 AI 易调试"的优点，又**稳定供给了 M3-M7 所需的非对称局面**，避免在对称局里靠运气/靠调参硬凑。AS-1~AS-6 与"对称自对弈"**并列运行**，不可互相替代。

### 6.5 机器可读的事件断言（回应评审 P1）

为使验收可复现、不依赖人工看日志，M1-M8 每条改写为**可查询的事件断言**（事件日志需包含对应字段，见第九节）。示例：

| 编号 | 机器可读断言 |
|------|------------|
| M1 | 存在对局满足：`kill_count_p0 > θ AND kill_count_p1 > θ` → 随后 `boss_awaken_early = true` → 终局 `outcome ∈ {double_lose}` |
| M2 | 存在对局满足：`kill_count_p0 ≫ kill_count_p1`，且终局 `outcome` **同时出现过** p0 胜、p1 胜、双输（说明"杀怪多"非单调胜负） |
| M3 | 存在事件序列：`weak_seek_alliance → alliance_form → alliance_end → attack(former_ally) → outcome recorded` |
| M4 | 存在事件序列：`alliance_end → attack_by_stronger → subsequent outcome ∈ {underdog_win, double_lose}` |
| M5 | `has_relic = true` 组的 solo 胜率**显著高于** `has_relic = false` 组（置信区间不重叠） |
| M6 | 存在 `heart_contested` 事件中 `contest_outcome = interrupted/changed_hands`；且 `killer == deliverer` 的比例**不过高**（见 6.7 M6 强化） |
| M7 | 存在事件序列：`tower_stock_placed_post_alliance → subsequent_win`（翻盘局） |
| M8 | 存在对局满足：前中期 `kill_count_both_low` → 终局 `outcome ≠ deadlock`（Boss 强化/时间压力迫使收束） |

**关键术语的统一定义**（避免口径模糊）：
- **停手**：连续 ≥ `T_hold` 秒（建议 10s）无主动杀怪行为（生存必需击杀除外）。
- **翻脸**：分两种，**结盟中途主动攻击**（立即破裂 + 惩罚仇恨）与**结盟倒计时结束后首次攻击**（破裂但不计惩罚）。断言中必须注明类型。
- **双输（统计派生标签）**：`double_lose` 不是运行时需要单独触发的系统结局，而是双方分别结算为失败后统计层使用的派生标签。系统只需独立结算每个玩家的胜负。
- **心争夺有效性**：若一方已出局，则心争夺事件不计入 M6 统计（避免"击杀者=交付者"必然成立污染数据）。

> 上述定义需与《AI数值测试与验收文档》第四节保持对齐，如有冲突以本文档为准并记录差异。

### 6.6 M2 口径澄清（回应评审 P2）

**问题**：v0.2 的 M2 写"杀怪方输或双输"，但核心机制文档的收益矩阵里，"你杀、他不杀"本应让你在 **PvP 端占优**，只是要面对**更早醒的 Boss**。两种期望不能都当验收方向。

**修订**：M2 不再期望"杀怪方一定输"，而是拆分为两个**独立的成立条件**：
- **M2a（PvP 端占优）**：单方杀怪方在**对对手的 PvP 层面**（击杀/压制）确实占优——即 `E(D|C)` 在 PvP 子收益上更高。
- **M2b（Boss 端代价）**：但单方杀怪方面对**更早/更强的 Boss**，导致**整体收益 T 不恒优于 R**（见 6.2.2 定义与 6.2.7 梯度测试）。

**即正确的期望是"杀怪让你在 PvP 占优、但在 Boss 端付出代价"，而非"杀怪方输"。** 若 M2a 不成立（杀怪连 PvP 都不占优），说明战力增益曲线过弱；若 M2b 不成立（杀怪无任何 Boss 代价），说明囚徒困境结构失效。

### 6.7 M6 强化（回应评审 P2）

v0.2 的"最后一击者不永远获胜"太弱。修订为**两条同时成立**：
- **M6a**：双方均存活期间，心发生**易手（changed_hands）或打断（interrupted）的比例 > 0**（建议阈值 > 10%，原型阶段可按样本调整）。
- **M6b**：`killer == deliverer`（击杀 Boss 者最终交付恶魔之心）的比例**不过高**（建议 < 70%，含容差）。

> 这两条确保"心争夺"是真实的争夺过程，而非"谁尾刀谁赢"的单调关系。

### 6.8 总体通过标准（v0.4：A / B / C / D 四层）

> ⚠️ **v0.4 将验收明确为四层。A 层只证明"系统能跑"；B 层（6.2 的 T>R>P>S）证明"囚徒困境在规则层面成立"；C/D 层区分"结构对"与"体验好"。**

**只有 A、B、C 三层同时通过，才可判定机制成立并冻结数值：**

1. ✅ **A 层**：M1-M8 全部至少触发过一次（受控场景 AS-1~AS-6 驱动 M3-M7），且事件断言（6.5）可判定；
2. ✅ **B 层 · 成立性**：锁定策略收益满足 **T > R > P > S**（6.2.5 主判据），含对称性校验（6.2.3）与梯度测试（6.2.7）；
3. ✅ **C 层 · 统计显著**：全部指标在**种子组 + holdout** 上通过区间门禁，DC ≈ CD（6.2.5 辅助判据）；
4. ✅ **D 层 · 体验质量**：D-1~D-4 **至少大部分满足**（允许迭代，不作为冻结硬门槛，但须记录偏离项）；
5. ✅ **AI 够用**：第十一节自检（含 5.3/5.4 相关的圣物/囤塔行为）通过。

> ⚠️ **v0.4 明确**：
> - **A 层单独通过 → 不得冻结**（机制可能只是"能跑"，如杀怪权重=0 或 =100 的反例）；
> - **B 层不通过（T>R>P>S 任一条反了）→ 改规则，不是调参**；
> - **C 层不通过（holdout 上排序崩塌）→ 回到参数校准，警惕针对训练种子的过拟合**；
> - **D 层不通过 → 允许带着"数值舒适度待优化"的标注冻结 v1，进入项目中后期打磨**。
>
> 这是与 v0.1/v0.2（"跑通即冻结"）最大的口径变化。

### 6.9 接近态分化验收（v0.5 新增，为 B 层提供自然事件源）

**设计假设（可验收）：**

1. 数值接近 + 对手未见偷杀 + `SAFE` → 双方克制率应明显高于随机，但不要求 100%；
2. 数值接近但刷新窗口内一方曾偷杀 / trust 偏低 → 应出现"一方克制、一方激进"或"双方激进"的分支；
3. 数值拉开 → 路线分化（领先 vs 落后）稳定出现，作为 AS-1~AS-6 之外的"自然事件源"；
4. 接近态的三种组合（CC / DC / DD）在自然对局种子组中都出现过，且能与 6.2 的锁定策略收益表相互印证。

**观测指标（记入第九节）：**

- 接近判定时的双方路线组合：克制-克制 / 克制-激进 / 激进-激进；
- 各组合后续 outcome：一方胜 / 双输 / 未完成；
- 单方激进分支是否出现若干局（用于证明克制不是无风险的免费选择）。

> **通过标准**：接近态"克制-克制"不是 100%；拉开态存在分化；单方激进至少出现在若干自然局或受控探针中。若不满足，先怀疑 5.6 的快照 / trust / 路线分支未生效，再怀疑数值。

## 七、与数值调试的闭环（如何用 AI 调数值）

### 7.1 四步法（不写复杂扫描，纯人工拍值 + 观察）

```
第 1 步 · 拍初始值
    ↓ 从设计文档取"示例值 / 中值"（如杀怪权重=3、结盟=30s、圣物减伤 50%）
第 2 步 · 跑基线（对称自对弈 + 受控场景 AS-1~AS-6，每场景 30-50 局 / 固定种子组）
    ↓ 记录 A 层触发 + B 层收益矩阵 + 胜率/双输率
第 3 步 · 先跑锁定策略收益矩阵，验证 B 层 T > R > P > S（6.2）
    ↓ 若排序不成立 → 先修收益结构（权重/曲线/减伤），再谈行为频率
第 4 步 · 对照清单、针对性调参
    ↓ 哪个行为未出现 / 哪个关系不成立 → 调对应参数 → 重跑
```

> 与 v0.2 的关键差异：**第 3 步提前**——先验证收益结构（B 层），再调行为频率（A 层）。这避免"行为都能触发但结构已死"的误判。

### 7.2 参数 → 行为映射表（调试时的"导航图"）

| 怀疑方向（行为未出现 / 关系不成立） | 优先调整的参数 |
|----------------------------------|--------------|
| A 层 M1 永不双输、Boss 太弱 | Boss 基础强度、强化速率、杀怪权重 |
| B 层 T>R>P>S 任一条反了（尤见 R>P） | 战力增益曲线 vs 提前苏醒代价曲线（**结构性**，可能非单一参数问题，回到 6.2.7） |
| T 过大 / 背叛恒优（T≫R） | 杀怪权重、Boss 提前苏醒惩罚、个人权重→恶魔分身阈值 |
| R≈P 或排序不显著（置信区间重叠） | 样本量、效用函数权重、进度信息延迟窗口、趋势感知阈值 |
| M3 结盟从不发生 | 结盟时长、结盟伤害/减伤加成、弱者血量阈值 |
| M4 翻脸无收益 | 翻脸仇恨惩罚、终局 solo 难度 |
| M5 圣物无关胜负 | 圣物减伤比例、Boss DPS |
| M6 永远尾刀获胜 | 心拾取读条时长、打断反馈、争夺窗口 |
| M7 囤塔无人用 | 配额、战力构成、Boss 对塔的响应 |
| M8 极端合作成僵局 | Boss 随时间强化幅度、海平面压缩速度 |

### 7.3 "够用"即可，不求最优

原型阶段的数值**不需要精确区间、不需要置信度分析**。只要：
- A 层 M1-M8 全部触发；
- **B 层 T > R > P > S 成立**（含对称性校验与梯度测试）；
- C 层在 holdout 上复现；
- D 层大部分满足（允许迭代）；
- 行为分布**不是 0% 也不是 100%**（说明存在真实选择，而非被锁定）；

即可将这组参数作为**"v1 初始数值包"**冻结，进入项目中后期的精细调优与多人格验证。

## 八、AI 决策落地实现规范（v0.7 概要）

> 本节把前文的"方向性设计"落成可实现的数据契约与主流程概要。**完整可执行规格见《AI 决策落地执行规格》（v0.2）**：字段结构、评分公式、阈值取值、Action 枚举与实现顺序均以该文件为准。若本节与规格冲突，以规格文件为准。

### 8.1 总原则：AI 决策收敛为纯函数

所有 AI 逻辑统一写成确定性的纯决策函数：**同种子、同输入必须同输出**。

```
ActionIntent = Decide(
    view      : PlayerView,   // 只读，玩家 UI 可见信息
    memory    : AiMemory,     // 每个 AI 自己的记忆
    config    : AiConfig,     // 所有参数外置，可热调
    gameTime  : float,
    seed      : int
)
```

决策函数内部**禁止直接读取 Unity 场景对象、对手内部状态或未公开信息**；需要随机时只允许由 `seed` 派生，保证可复现。

### 8.2 数据契约（必须明确命名与字段）

**`PlayerView`（公开可见信息，与 HUD 对齐）**

```text
selfHp / oppHp
selfPower / oppPower
bossProgress              // 按 20-40s 刷新
bossProgressRate
seaLevel / playTime
selfTowerPlaced / oppTowerPlaced
selfTowerStock / oppTowerStock
selfHasRelic / oppHasRelic
allyState                 // Player / Boss / None
eventQueue                // 本决策周期内的公开事件
```

**`AiMemory`（每个 AI 独立维护）**

```text
lastStrategySnapshot
snapshotPhase
trustScore
recentlyBetrayed
killStreak
currentRoute
routeChangedAt
```

**`AiConfig`（ScriptableObject 或 JSON，全部外置）**

```text
samplePeriod               // 10s
phaseA / phaseB            // 4 / 9
safeQuotaKillsPerWindow
watchRate / urgentRate
closeGapThreshold          // 初始 ±0.25
aggressionThreshold
routeHoldTime              // ≥ 1 个快照周期
trustDecay
aggressionWeights          // w1-w5，初始 1.0
```

**`ActionIntent`（决策输出）**

```text
movementTarget
attackTarget
channelAction              // 开箱 / 拾取心 / 采集等
placeTower / holdTower
allianceAction             // 申请 / 接受 / 拒绝 / 无
priority
reasonCode                 // 供日志与断言使用
```

### 8.3 决策主循环：事件级与战略级分离

**事件级（每 0.5s 或即时）**

```text
1. view = PlayerViewBuilder.Build()
2. 血量 < 生存阈值          → 治疗 / 逃跑（最高优先级，不使用旧快照）
3. eventQueue 非空
   （被攻击 / 结盟申请 / 心出现 / Boss 结盟发起）→ 立即响应
4. 否则 → 取当前 route 对应的 ActionIntent
```

**战略级（只在快照点执行，默认每 10s）**

```text
if gameTime % samplePeriod == 当前 AI 相位:
    1. 更新局势快照（SAFE / WATCH / URGENT）
    2. 更新对手评估与 trustScore
    3. 若 routeHoldTime 已结束 → 重新计算路线（带滞回）
    4. 记录 routeChanged 日志
```

事件响应永远即时，不允许被快照延迟阻塞；快照只决定"当前走什么路线"。

### 8.4 对手评估与 trust 的可计算规则

trust 不猜测意图，只累计公开可推断的证据：

```text
oppContributionThisWindow =
    本窗口共享进度增量 - 自己已知击杀贡献

if oppContribution > safeQuota × 1.5 → 激进证据
if oppContribution < safeQuota × 0.5 → 克制证据
if 结盟期间攻击我 / 拆我塔            → 背叛证据
if 主动申请结盟                        → 合作信号
```

更新规则：

```text
trustScore = clamp(
    trustScore
    + 激进证据 × (-0.3)
    + 克制证据 × (+0.2)
    + 背叛证据 × (-0.5),
    0, 1)

若连续 3 个刷新周期无新证据 → trustScore 向 0.5 缓慢衰减
```

以上系数为初始建议，实际值在沙盘阶段校准，且只改 `AiConfig`，不改代码逻辑。

### 8.5 路线切换：明确触发条件与滞回

```text
gap = (selfPower - oppPower) / max(1, max(selfPower, oppPower))

if 进入终局模式                → Layer 3 终局行为（覆盖路线）
else if 血量 < 生存阈值         → 生存行为（最高优先级）
else if gap > +cfg_gapLead     → PRESS（领先，压制对手）
else if gap < -cfg_gapLead     → CATCH_UP（落后，追赶 / 结盟准备）
else 数值接近：
    aggressionScore =
        baseRisk
      + w_killDelta × 对手偷杀证据
      + w_leadPower × powerGap
      + w_window × 刷新窗口剩余诱惑
      + w_trust × (50 - trustScore) / 50
      - w_rate × Boss 进度风险
      - w_survive × 自保需求
      - w_allianceReady × 结盟可用加成

    if aggressionScore > aggressionThreshold → AGGRESSIVE
    else                                     → RESTRAIN
```

> 权重与阈值取值见《AI 决策落地执行规格》8.1 配置表；本节不再维护第二套权重。

切换约束：

- 路线只允许在战略快照点切换；
- 两次切换间隔 ≥ `routeHoldTime`；
- 阈值附近使用滞回，禁止因分数抖动反复横跳；
- 若双方状态与输入完全相同，选择同一条路线是被允许的，不需要强制分裂。

### 8.6 路线模板：只改行为约束，不改底层操作

| 路线 | 自然怪击杀 | 精英怪击杀 | 开箱倾向 | 塔放置 | 结盟接受度 |
|------|-----------|-----------|---------|--------|-----------|
| `RESTRAIN` | 0 | 仅必需 | 高 | 延迟放置 | 正常 |
| `AGGRESSIVE` | 配额 × 1.8 | 高 | 中 | 正常 | 低 |
| `PRESS` | 配额 × 1.2 | 高 | 低 | 正常 | 低 |
| `CATCH_UP` | 低 | 仅必需 | 很高 | 优先囤塔 | 高 |

路线只改变资源管理倾向与目标选择，不覆盖 8.3 的事件响应、生存和终局行为。

### 8.7 无头数值沙盘先行

囚徒困境收益结构验证不依赖完整 3D 场景。实现顺序建议：

```text
第 1 步：无头数值沙盘
  输入：杀怪权重、成长曲线、Boss 苏醒阈值、Boss 强化曲线
  动作：每窗口选择 C 或 D
  输出：CC / DD / DC / CD 的期望胜负、双输率、U 均值

第 2 步：若沙盘无法满足 T > R > P > S → 修机制，不进入场景
第 3 步：沙盘成立后，再接入 Unity 场景做 M1-M8 烟测
```

沙盘用于验证收益结构与快速调参；最终数值仍需在 Unity 场景内回归确认。

### 8.8 日志与策略探针

每次决策至少记录一行：

```text
time | seed | ai | situation | route | trustScore |
oppInference | action | reasonCode
```

同时提供外部覆盖配置：

```text
policyLock   // 测试时强制 CC / DD / DC / CD，正常对局为 off
scenarioId   // 加载 AS-1 ~ AS-6
phaseOverride // 测试快照相位
```

所有 A/B 层结论由日志断言自动生成，不依赖人工观看。

### 8.9 建议实现顺序

1. 先实现 `PlayerView`、`AiMemory`、`AiConfig`、`ActionIntent` 四类数据契约；
2. 实现无头沙盘并跑通 B 层收益矩阵；
3. 实现 `Decide` 纯函数与路线模板；
4. 在 Unity 中接入公开信息构建器与场景集成；
5. 补齐事件日志、策略探针和 AS-1~AS-6；
6. 最后做参数校准与 holdout 验证。

## 九、数据记录与可复现性

复用《AI数值测试与验收文档》的约定，原型阶段简化为：

1. **确定性**：每局固定随机种子，同参数同种子可复现；关键局用固定种子组（**30-50 局/组**，见第十节 P1）。
2. **快照**（v0.3 扩充字段，回应评审 P0-3）：每 1 秒记录——
   - 双方：血量、战力、**已放置塔数 / 背包囤塔数（区分）**、**当前是否持有圣物**、结盟状态与对象（Player/Boss）、心位置、水位；
   - AI 决策层：当前路线（克制/激进/追赶/…）、对手快照推断、`trustScore`、快照相位（`gameTime % T`）；
   - 全局：Boss 进度/形态/强化层、**Boss 当前结盟对象**、提前苏醒次数。
3. **事件日志**：Boss 提前苏醒、结盟（区分 Player/Boss 类型）、翻脸（区分中途/结束）、心掉落/拾取/打断/易手、Boss 击杀、玩家出局、双方分别结算失败（统计层双输）——全部带时间戳。
4. **运行门禁（原型简化版）**：单局出现卡死 / 事件缺失 / 异常中断即标为无效，不计入 A/B 层统计；无效局率过高时先修 AI，再调数值。
5. **修改审计**：每次改参记录（参数、原因、样本量、结果差异），保证可回溯。

## 十、统计口径与样本量（v0.3 修订，回应评审 P1）

### 10.1 问题：v0.2 的"20-30 局 + 40-60%"不可靠

- 20-30 局下随机波动很容易让胜率显示成 35%/65%，双输率也可能因恰好 0 局而虚高置信度；
- **同质 AI 的 50/50 主要由对称性保证，不能作为平衡性证据**，只能暴露出生点/标签不对称等 bug。

### 10.2 修订方案

1. **种子组规模**：每场景 **30-50 局/种子组**（沿用《AI数值测试与验收文档》默认），A 层与 B 层统一采用。
2. **holdout 种子（关键）**：保留一批**从未参与调参的 holdout 种子**。任何参数调整后，**只在训练种子上调参；最终判定一律用 holdout 种子重跑**——防止"针对训练种子过拟合、换种子就崩"。**holdout 通过才允许冻结数值。**
3. **区间门禁（替代单点阈值）**：胜率、双输率、M5/M6 比例等指标改用**置信区间 / 宽松容差**门禁。例：
   - 双方胜率：`[35%, 65%]`（含容差，取代严格 40-60%，因 30 局样本方差大）；
   - 双输率：`≤ 25%`（上限略放宽，因原型阶段行为粗糙）；
   - M5 圣物效应：持有组 vs 未持有组胜率的 **95% 置信区间不重叠**；
   - M6：易手/打断比例 `> 10%`、击杀者交付率 `< 70%`。
4. **对称性的正确使用**：对称自对弈的 50/50 **只用于**：① 检测出生点/标签不对称 bug；② 作为 B 层收益矩阵的**基准行（C|C、D|D）**。它**不构成"平衡性达标"的证据**。

> 以上阈值（35/65、25%、10%、70%）为**原型阶段起始值**，可在跑基线后按实际方差校准，校准理由须记入修改审计。

## 十一、AI "够用"自检（进入数值调试前的三道门）

在正式调数值前，先跑这三个**人工检查**（各 5 局、极端参数）：

| 检查 | 操作 | 通过标准 |
|------|------|---------|
| **参数敏感性** | 杀怪权重 3 → 10 | AI 杀怪频率明显下降 |
| **结盟触发** | 己方血量 30% + Boss 进度 85% | AI 主动申请结盟（区分 Player/Boss 类型） |
| **翻脸行为** | 两 AI 结盟后等待结束 | 至少一方在结束后攻击（含两种翻脸类型判定） |

**三项全部通过 → AI "够用"，可进入第七节的四步调参循环。**

> v0.3 新增建议：自检可再补两项（非强制，视实现进度）——**圣物行为**（持有圣物时是否倾向 solo）、**囤塔行为**（终局是否放置背包囤塔）。这两项若失败，会直接导致 M5/M7 无事件源。

## 十二、阶段出口（何时算"原型完成"）

满足以下全部条件，即可宣告原型阶段完成，冻结 v1 初始数值包，移交项目中后期：

1. ✅ A 层：M1-M8 全部至少触发过一次（受控场景 AS-1~AS-6 驱动 M3-M7），事件断言可判定；
2. ✅ B 层：锁定策略收益满足 **T > R > P > S**（6.2），含对称性校验与梯度测试，且在 **holdout 种子**上复现；
3. ✅ 统计：全部指标在种子组 + holdout 上通过区间门禁（第十节）；
4. ✅ 第十一节自检通过（AI 够用，含可选的圣物/囤塔项）；
5. ✅ 无效局率可控（卡死/事件缺失不泛滥）；
6. ✅ 一组可复现的初始数值参数（配置表形式，外置、非硬编码）。

> **出口定义的意义**：明确"做到什么程度就可以停"。原型阶段最大的风险是过度打磨——记住，现阶段你只需要证明**机制活着、收益结构成立**，剩下的交给中后期。
>
> ⚠️ **v0.3 明确：第 1、2、3 项任一不满足，即使 A 层烟测全部触发，也不得冻结数值包。**
